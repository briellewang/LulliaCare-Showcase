# LulliaCare 技术架构

## 总体架构

LulliaCare 采用移动端与 API 服务分离的结构。Flutter 负责交互与本地状态，FastAPI 负责身份、业务数据、内容安全与 AI 编排。

```text
Flutter App
  ├── Feature 页面
  ├── 共享组件
  ├── API Gateway / Models
  └── 本地状态持久化
          │
          ▼
FastAPI
  ├── API 路由与参数校验
  ├── 用户 / 社区 / 小组服务
  ├── LangGraph AI 子系统
  ├── 内容审核与匿名化
  ├── Redis 埋点与降级队列
  └── SQLAlchemy / MySQL / Alembic
```

## 移动端设计

- 按 `core / features / shared` 分层；
- 统一 API Gateway 隔离网络实现与页面；
- API 地址通过编译变量注入，业务代码不硬编码环境；
- 使用命名路由与共享组件统一交互；
- 中英文文案由 `gen-l10n` 生成；
- 使用 `shared_preferences` 持久化设备 ID、Token、角色和会话状态；
- 测试中可替换 Gateway，避免依赖真实网络。

## 后端设计

- FastAPI 路由层只负责参数校验、服务调用与响应组装；
- SQLAlchemy 2.0 管理 ORM，Alembic 维护线性迁移；
- MySQL 保存业务数据，Redis 承担异步埋点队列并支持内存降级；
- JWT 分为强制鉴权与可选鉴权两种使用方式；
- 内容审核、匿名化、日志和事件埋点作为横切服务复用。

## AI 编排

AI 请求不是一次直接模型调用，而是一条可控流程：

```text
加载上下文
  → 安全检查
      ├── 高风险：输出安全资源并结束
      └── 常规：意图识别 → 角色回复 → 行动建议 → 输出格式化
```

模型访问通过 Provider 抽象，业务逻辑不依赖单一厂商。三层记忆分别承担近期上下文、事实连续性与跨会话陪伴。

## 关键工程取舍

### 为什么采用匿名设备身份

MVP 阶段优先降低首次使用门槛，同时将真实标识与前台化名分离。正式账号体系通过预留字段和后续合并流程扩展。

### 为什么将安全检查放在生成之前

高风险表达不应继续进入普通角色对话。前置分流能减少不合适的拟人回复，并让紧急资源更快到达用户。

### 为什么保留本地降级

Redis 不可用时，埋点不应阻断核心对话链路。系统会退化到进程内队列，优先保证主要功能可用。

### 为什么展示仓库与源码仓库分离

展示仓库服务面试官和产品阅读者，强调故事、决策和成果；源码仓库服务开发者，保留完整实现、测试和版本历史。两者关注点不同，分离后更容易维护。
